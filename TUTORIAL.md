# Lab 1 — Tutorial: the CORDIC accelerator from RTL to layout

A guided run of the whole flow on the accelerator that ships with this
repository, with the output you should get at every step. Do this once, in
order, before you start on your own accelerator.

Prerequisite: [SETUP.md](SETUP.md) finished. Every command below runs from the
`lab1` directory.

```bash
source /oss-tools/init.sh                    # on isaserver
source /eda/scripts/init_design_vision       # Design Compiler, PrimePower
source /eda/scripts/init_cadence_2020-21     # Innovus
source /eda/scripts/init_questa_core_prime   # QuestaSim
export IHP_PDK_ROOT=/oss-tools/pdk/ihp-sg13g2
```

`make help` lists every target.

Six stages, and each one produces something the next one consumes:

```
   model ──► RTL ──► netlist ──► layout
     │        │         │          │
  vectors   TEST     timing      timing
            PASSED    area      area DRC
                        │          │
                        └── power ─┘
```

## 0. What you are given

A **working** accelerator. Unlike Lab 0, nothing here is a stub: the point of
this tutorial is to run a flow that already closes, so that when you replace
the RTL with your own you know the flow is not what broke.

```
rtl/cordic_pkg.sv              fixed-point formats, the atan ROM, saturation
rtl/cordic_rot.sv              the rotator (from the Example Cookbook)
rtl/cordic_accel.sv            OBI manager + CSRs wrapped around the rotator
rtl/cordic_accel_reg_{pkg,top}.sv   generated by reggen -- NOT in git
data/cordic_accel.hjson        the register description reggen reads
model/cordic_golden.py         the golden model -> vectors/*.hex
model/check_bitexact.py        pins the model to the cookbook's CORDIC
tb/tb_cordic_accel.sv          one self-checking testbench, both simulators
implementation/
  tech/generic/                behavioural cells      (simulation)
  tech/sg13g2/                 real library cells     (synthesis)
  design_compiler/             logic synthesis        + its README
  innovus/                     place and route        + its README
  power_analysis/              switching-activity power + its README
cordic_accel.core  Makefile    the build
```

**The accelerator.** A CSR block you program with a source pointer, a
destination pointer, an element count and two seeds; it then reads angles over
OBI, rotates the seed vector by each one, and writes the results back. One
clock, one reset, an asynchronous active-low reset, and a `testmode_i` that
bypasses the internal clock gate.

Read `rtl/cordic_accel.sv` before you run anything. Twenty minutes now saves
an afternoon later.

## 1. Fetch the IPs and generate the CSRs (once)

```bash
make vendor
make regs
```

`make vendor` copies pinned snapshots of four pulp-platform IPs into
`vendor/pulp_platform/`. Not submodules: `util/vendor.py` reads a
`.vendor.hjson` naming a repo and a revision, copies the tree without its
`.git`, and writes a `.lock.hjson` recording what it actually got. Same tool
and same reasoning as Lab 0.

`make regs` runs OpenTitan's `regtool.py` over `data/cordic_accel.hjson` and
writes three files:

```
generated rtl/cordic_accel_reg_{pkg,top}.sv and sw/cordic_accel_regs.h
```

The `.sv` pair is the CSR block the RTL instantiates; the `.h` is the header
the Lab 3 driver will include. **None of them are in git** — they are
generated, and the `.hjson` is the source of truth. Change the register map by
editing the hjson and re-running `make regs`, never by editing the generated
files.

The register map it produces:

| offset | name | meaning |
|--------|------|---------|
| `0x00` | `CTRL` | bit 0 `START`, write-1 pulse |
| `0x04` | `STATUS` | bit 0 `DONE`, bit 1 `BUSY` |
| `0x08` | `N` | element count |
| `0x0C` | `SRC` | source base address |
| `0x10` | `DST` | destination base address |
| `0x14` | `SEED_X` | x0, Q1.14 signed |
| `0x18` | `SEED_Y` | y0, Q1.14 signed |

## 2. Golden vectors, and the model behind them

```bash
make vectors
```

```
64 angles -> vectors/theta.hex, vectors/golden.hex, vectors/golden_swap.hex, vectors/config.txt
```

`model/cordic_golden.py` is the reference. It computes what the hardware must
compute, in Python, with the same fixed-point format and the same truncation —
and the testbench compares the RTL against it bit for bit, not approximately.

Two checks come with it, and they answer different questions:

```bash
make model-check     # is the model right?
make bitexact        # is the model the same one the cookbook uses?
```

```
cookbook model : 4401 cases, 0 mismatches
cookbook vectors: 315 cases, 0 mismatches
```

`model-check` compares the model against `math.cos`/`math.sin` — it tells you
the CORDIC is a correct CORDIC. `bitexact` compares it against the Example
Cookbook's CORDIC, whose VHDL and SystemVerilog you have already seen. Together
they mean your RTL, the cookbook's RTL, the Python model and the C kernel from
Lab 0 all produce the *same integers*.

That chain is the shape your own accelerator should have. One golden model,
RTL that matches it bit for bit, and a self-checking testbench.

## 3. Simulate, on both simulators

```bash
make sim
```

```
[TB] 64 angles from /home/<you>/isa-lab1/lab1/vectors/
[TB] run1 (cos/sin): 64/64 results match the golden model
[TB] run2 (seed +90): 64/64 results match the golden model
TEST PASSED
```

Then the same testbench on the other simulator:

```bash
make questa
```

Same source, same vectors, same `TEST PASSED`. The comparison happens **inside
the testbench**, not by diffing files afterwards, so the exit code means
something and you can put it in CI.

Why both? Verilator is fast and free and you will use it constantly; QuestaSim
is what the gate-level flow needs, because Verilator cannot back-annotate SDF
timing. A testbench that only ever compiled on one of them would have to be
rewritten at exactly the point where you least want surprises.

Look at the waveforms once:

```bash
make waves           # writes an FST; open it with gtkwave
```

And before you commit anything:

```bash
make lint            # Verilator lint of the synthesisable RTL only
```

## 4. Synthesis

Full walkthrough: **[implementation/design_compiler/README.md](implementation/design_compiler/README.md)**.
Read it and run the flow by hand, one command at a time, in `dc_shell`. Then
come back and use the target:

```bash
make synth
```

The first run also compiles the PDK's Liberty into a `.db` and caches it under
`implementation/design_compiler/db/`; that needs a Library Compiler licence and
takes about a minute. The whole thing takes **three to four minutes** on the
server.

What you should get:

```
implementation/design_compiler/netlist/
    cordic_accel.v      the gate-level netlist
    cordic_accel.sdf    cell and net delays
    cordic_accel.sdc    the constraints, carried forward
    cordic_accel.ddc    Design Compiler's own database
```

Check three things, in this order, every time:

**1. Did it use the real library?** If the technology setup fails, `dc_shell`
falls back to its built-in `gtech` library and *keeps going* — you get a
netlist of generic gates that means nothing.

```bash
grep -c sg13g2_ implementation/design_compiler/netlist/cordic_accel.v   # ~2900
grep -c -i gtech implementation/design_compiler/netlist/cordic_accel.v  # 0
```

**2. Does it meet timing?**

```bash
grep slack implementation/design_compiler/reports/timing.rpt
#   slack (MET)    0.00
```

**3. How big is it?**

```bash
tail -3 implementation/design_compiler/reports/area.rpt
#   Total    22148.2671   22678.1856
```

About **2483 cells** at 10 ns (100 MHz), slow corner, and 43 821 µm² of core
after place and route. Those two numbers — the frequency you met and the area
it cost — are the result. Neither means anything without the other.

Note what the slack says: **0.00**. `compile_ultra` meets the constraint and
then spends whatever is left on area, so the reported slack sits near zero
whatever period you ask for. A relaxed clock buys you a smaller, cooler
design, not a slacker critical path.

### The experiment to run here

Find the maximum frequency by sweeping the constraint until the slack goes
negative:

```bash
for p in 8.0 6.0 5.0 4.0 3.0 2.5 2.0; do
  make synth CLK_PERIOD=$p
  echo -n "$p ns: "
  grep -h slack implementation/design_compiler/reports/timing.rpt
done
```

That loop is the reason the flow is in a script instead of typed into a shell.

### Clock gating, which you will be asked about

Look at what the tool inserted:

```bash
grep -c SNPS_CLOCK_GATE implementation/design_compiler/netlist/cordic_accel.v
grep -o 'sg13g2_s\?lgcp_1 [A-Za-z0-9_]*' implementation/design_compiler/netlist/cordic_accel.v
```

You will find **two different kinds** of clock gate, and the difference is the
whole of §5b and §5c of the synthesis README:

- `sg13g2_lgcp_1`/`sg13g2_slgcp_1` inside `SNPS_CLOCK_GATE_HIGH_*` wrappers —
  eighteen of them, inserted automatically by `compile_ultra -gate_clock`, one
  per enable-driven register bank.
- `i_cordic_clk_gate_i_icg` — the one the *design* asked for, wrapped around the
  rotator, because you know the rotator is idle for whole runs and the tool
  does not.

And §5c makes the point that neither of them is how a real chip saves power:
that is done by switching the whole peripheral's clock off from the SoC clock
controller. Read it before you write your report.

## 5. Place and route

Full walkthrough: **[implementation/innovus/README.md](implementation/innovus/README.md)**.
Again: do it in the GUI first. Place and route is the one stage where you can
*see* the consequences of your decisions, and the picture is the point.

```bash
cd implementation/innovus
innovus -stylus
```

then, one at a time, following the README: `source scripts/globals.tcl`,
`helpers.tcl`, `init.tcl`, `floorplan.tcl`, `powergrid.tcl`, `place.tcl`,
`cts.tcl`, `route.tcl`. Watch the layout after each.

Log in with **`ssh -X`** (and XQuartz running, on a Mac) or the GUI cannot
open. This is verified working on isaserver.

Then the scripted version:

```bash
make pnr-all             # the usual one: route, then optimise and export
make pnr                 # just up to the routed design (post_route.db)
make pnr-opt             # just the optimisation and export, from that db
make pnr-gui             # the flow with the GUI open (needs `ssh -X`)
make pnr PNR_UTIL=0.75   # denser floorplan
```

**Why two steps.** On Innovus 20.11 both `opt_design -post_route` and
`route_eco -fix_drc` fail in the same session that did the routing — and
`opt_design` fails badly, leaving ECO cells that were never routed (DRC
goes from 7 to 1754). The same commands on the same database in a *fresh*
session work. So `make pnr` stops at `post_route.db` and `make pnr-opt`
picks it up. The header of `scripts/run_pnr_opt.tcl` has the measurements.

It matters: without the second step hold is **−0.220 ns**; with it, hold is
**−0.002 ns** and the DRC count is zero.

Outputs land in `implementation/innovus/artefacts/`:

```
artefacts/reports/     one log and a set of reports per stage
artefacts/db/          post_<stage>.db -- restart from any stage
artefacts/export/      the netlist, SDF, SPEF and GDS
```

The four exported files each have exactly one consumer, and the first one
matters for the next section: `cordic_accel_pnr.v` is the netlist **with the
clock tree in it**. Design Compiler's netlist has an ideal clock — no tree, no
buffers, no skew — and the clock tree is usually a large share of a block's
power.

### One script per stage, on purpose

To retry CTS with a different skew target without redoing placement:

```tcl
innovus -stylus
source scripts/globals.tcl ; source scripts/helpers.tcl
set REPORT_DIR $design(REPORT_DIR)
read_db artefacts/db/post_place.db
source scripts/cts.tcl          # after editing it
```

That is the difference between a sweep that takes an afternoon and one that
takes a week.

## 6. Power

Full walkthrough: **[implementation/power_analysis/README.md](implementation/power_analysis/README.md)**.

```bash
make power
```

Two steps behind that one target. First a **gate-level** simulation in
QuestaSim: the synthesised netlist, the library's Verilog cell models, and the
SDF back-annotated so every gate takes as long as the real cell does. It runs
the same testbench and must also print `TEST PASSED` — if the netlist does not
compute the right answer, its power is not interesting. It records every
transition into a VCD.

Then **PrimePower** maps that activity onto the netlist and computes watts.

On the shipped design at 100 MHz, typical corner, you should get about
**0.813 mW**, with 100 % of the 2577 nets annotated from the VCD, split
roughly 52 % combinational / 34 % clock network / 14 % registers, and
leakage at 0.06 %.

Two things in that split are worth a paragraph in your report. The clock
network is a third of the total *before* place and route builds a real
clock tree — no amount of fine-grained gating touches it, because the gates
hang off the tree's leaves while the tree keeps toggling. And leakage is
essentially nothing at 130 nm and 25 °C, which is exactly why the interesting
power question at this node is dynamic and not static.

> **The post-synthesis run is done at zero delay** — see the long comment in
> `questa/gate_sim.do`. Annotating the Design Compiler SDF onto this netlist
> currently makes the self-check fail for reasons not yet understood, so the
> flow leaves it off. You therefore get every real transition but **no glitch
> power**, which makes this number a lower bound. Say so when you report it,
> and do the post-layout run (§8 of the power README) for the real figure.

```
reports/cordic_accel_power.rpt          the total -- start here
reports/cordic_accel_hier.rpt           where it goes
reports/cordic_accel_leaf.rpt           per cell
reports/cordic_accel_clock_gating.rpt   how much of the design is gated
reports/cordic_accel_not_annotated.rpt  what the VCD did NOT cover
```

**Read the last one first, every time.** If the VCD's hierarchy does not line
up with the netlist's, `read_vcd` annotates nothing, *silently*, and
`report_power` falls back to the default toggle rate — the same guess
`report_power` made in synthesis. You get a plausible number that measures
nothing. The not-annotated report is the only thing that tells you which
happened.

Why this instead of the synthesis estimate: dynamic power is
`alpha * C * V² * f`, and `alpha` — how often each node actually toggles —
depends on the *data*. No tool can derive it from a netlist. Design Compiler
guesses; here you measure.

## 7. What to do when a stage fails

The failure modes are stage-shaped, and the first error is always the real one:

| symptom | look at |
|---------|---------|
| `TEST FAILED`, a few mismatches | your RTL; compare against `model/cordic_golden.py` |
| `TEST FAILED`, all mismatches | the vectors, or `SRC`/`DST`/`N` programming |
| synthesis finishes in 3 s, empty netlist | `reports/synth.log` from the **top** |
| netlist full of `GTECH` | the library setup failed; `target_library` was empty |
| Innovus stops in `init` | `artefacts/reports/01_init.log`, grep for `ERROR` |
| routing will not converge | congestion. Lower `PNR_UTIL`, back in the floorplan |
| power looks like the synthesis estimate | `*_not_annotated.rpt`: the VCD strip path is wrong |

Reading a 20 000-line log from the bottom is the single most common way to
waste an hour. The last two hundred errors are consequences of the first one.
